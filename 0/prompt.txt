I reviewed the extension against your goal: the LLM sees only redacted data, and anything handed back to Pi gets the original values restored. It doesn't meet that goal yet. Redacting works on single messages, but nothing restores the original values, and the numbering it uses couldn't be reversed reliably even if something did.

**State of the repo:** typecheck passes. Tests pass 294 of 300. The 6 failures are timeouts and speed limits on large inputs (a 10k-character input took about 14.6s), not wrong answers.

## Blocking problems

**1. Nothing gets restored.** `RedactionResult.restore` and `RedactorService.restore` exist, but no hook calls them. `src/hooks/index.ts` only handles `input`, `tool_result` and `context`, and all three only redact. In practice:

- The model's replies show raw placeholders like `[EMAIL_1]` to the user.
- **Tool calls run with placeholders.** If the model reads a file containing an email address and then edits it, the `edit`/`write` call writes `[EMAIL_1]` into the file. The same goes for `bash` commands built from redacted values. This is the most serious practical risk, because it quietly changes the user's files.

**2. Placeholders aren't stable, so they can't be reversed.** Every `redact()` call numbers from 1 again. I confirmed this with the real model:

```
redact("Contact alice@acme.com")  → "Contact [EMAIL_1]"
redact("Also loop in bob@globex.com") → "Also loop in [EMAIL_1]"
svc.restore("Send it to [EMAIL_1]") → "Send it to bob@globex.com"   ← wrong person
```

The `context` hook redacts each message separately, so a conversation mentioning "Sarah Johnson in Berlin" and "Michael Brown from Munich" reaches the LLM as `[GIVEN_NAME_1] [SURNAME_1]` twice. The model can't tell the two people apart. On top of that, the service's shared restore map lets the last write win, and `Promise.all` makes the order racy.

Reversible tokenization needs a **session-scoped vault**:

- a two-way map from original value to token;
- the same value always gets the same token;
- numbering keeps counting up and never repeats within the session;
- the map is saved with `pi.appendEntry` so it survives a session reload or resume.

**3. Some messages are never redacted.** The `context` hook only looks at `msg.content` and only at blocks of type `text`. It skips:

- `bashExecution.output`, so the output of a user's `!cat .env` reaches the model unredacted;
- `compactionSummary.summary` and `branchSummary.summary`;
- assistant `thinking` blocks and `toolCall.arguments`.

**4. Restore is easy to fool.** If a file already contains the literal text `[EMAIL_1]`, it passes through redaction unchanged and is later "restored" to someone's real email address. Restore is also exact-match only, so if the model writes `EMAIL_1`, `[Email_1]` or `[ EMAIL_1 ]`, the placeholder is left as is. Tokens need a less collision-prone format, and any literal token text already in the input should be escaped.

## Design decision to make

Right now the user's prompt and tool output are stored redacted in the session (`input` and `tool_result` overwrite them). Compaction calls the model directly through `completeSimple`, which skips both the `context` and `before_provider_request` hooks. So storing redacted text is currently the only thing keeping compaction from leaking PII. Once the vault exists, I'd recommend this:

| Hook | Role |
| --- | --- |
| `input`, `tool_result`, `context` | Redact through the vault. Matches the vault already knows can be replaced with fast exact string matching, so most messages skip the model entirely. |
| `tool_call` | Restore the arguments in place in `event.input`, at any nesting depth. This is what Pi expects. |
| `message_end` | Restore the assistant's text so the user sees real values. The next `context` pass re-redacts it the same way, because the vault is stable. |
| `session_before_compact` | Supply a compaction built from redacted messages, or the plaintext assistant replies leak during compaction. |

The trade-off: the session file on disk will hold plaintext assistant messages. If that's not acceptable, keep everything redacted at rest and restore only for display and tool calls.

## Smaller issues

- The name model misses names fairly often at the 0.85 confidence threshold: `"Ping Sarah at …"` left `Sarah` unredacted. Names are the core PII here, so recall should be tested properly.
- Speed: the `context` hook runs the model again on every message before every LLM call, so the cost grows with the length of the conversation. The vault, or a cache keyed by message, fixes this and the timeouts above.
- `dispose()` is never called on `session_shutdown`, and `/pii` settings aren't saved.
- Leftover code: the hard-coded `[REDACTED:API_KEY]` special case, and a restore helper that duplicates `lastRestoreMap`. The repeat-match pass also adds duplicate entries, which inflates `count`.
- The README says context handling is non-destructive, but `input` and `tool_result` overwrite the stored session.
- The test suite (about 5,000 lines) never checks the full loop of redact → LLM → restore → tool call. Several tests check per-call numbering, which is exactly the behaviour that breaks reversal in point 2.

I'd fix these in this order: build the vault, add restore in `tool_call` and `message_end`, cover the missing message types in `context`, then sort out compaction. I can start on the vault if you want.
